# Демонстрационный кейс: изменение клиентского API

**Данные вымышлены. Это не проект KoronaTech, медицинской организации или какого-либо реального заказчика.**

## Запрос бизнеса
Открыть партнёрский API для нового сервиса. Цель: ускорить подключение партнёров, не допустить утечек или простоев.

## Активы и границы
Демо API gateway, демо БД клиентов, токены доступа, система журналирования, партнёрский контур.

## Сценарий риска DEMO-R001
Ошибки авторизации уровня объектов позволяют получить данные другого клиента. Возможные последствия: раскрытие данных, нарушения договорных обязательств, снижение доверия.

## Оценка (учебная)
Исходные L=4, I=4, 16/25, высокий. После проверки объектной авторизации, тестов, rate limiting и мониторинга оценка **предварительно** L=2, I=4, 8/25, умеренный. Снижение не считается подтверждённым до получения доказательств выполнения.

## Варианты решения
A. Выпустить как есть — не рекомендовано.
B. Выпустить после выполнения обязательных мер, проверки и повторной оценки — рекомендовано.
C. Отложить интеграцию, если меры нельзя обеспечить в срок.

## Требуемые доказательства
Результаты тестов авторизации; протокол архитектурного ревью; owner approval; monitoring runbook; результаты повторной оценки.

## Решение
**На рассмотрении** у бизнес-владельца. В GitHub не хранить реальные учётные данные, токены, сведения о конкретных уязвимостях и внутренние документы.
